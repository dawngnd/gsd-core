<title>Add writeResolvedSection and updateApprovalStatus helpers to ndd-discuss-spec.cts</title>

</read_first>

<action>
Extend `src/ndd-discuss-spec.cts` with two new exported functions and supporting types:

1. **Types**: Define `Resolution` with fields `original_ref: string` (section + text reference), `decision: string` (what was decided), `source: string` (who/what provided the answer), `resolved_at: string` (ISO timestamp). Define `ApprovalStatus` as `'draft' | 'discussed' | 'approved'`. Define `UpdateApprovalResult` as ok/error discriminated union.

2. **writeResolvedSection(changeSpecPath: string, resolutions: Resolution[]): void**:
   - Read existing CHANGE-SPEC.md content from `changeSpecPath`
   - Per D-04: preserve all original sections intact (ambiguities, conflicts, open-questions remain)
   - Per D-05: append a `## Resolved` section at the end (before any existing Resolved section if re-running — detect and replace)
   - Each resolution rendered as a bullet: `- **[original_ref]**: decision (source: source_ref) — resolved_at`
   - Per D-20: Also append `## Acceptance Criteria` section if not already present (empty placeholder with instruction comment)
   - Per D-20: Also append `## Scope` section with `### In Scope` and `### Out of Scope` subsections if not already present
   - Write back using `platformWriteSync`

3. **updateApprovalStatus(projectRoot: string, changeId: string, status: ApprovalStatus): UpdateApprovalResult**:
   - Per D-08: Dual-write approval state:
     a. Read STATUS.json via the intake module pattern, set `status` field to the new value and `phase` to `'discuss'` (or `'approved'` if status is `'approved'`), write back
     b. Read CHANGE-SPEC.md, find the `## Draft / Approval Status` section, update the `- Status:` and `- Approval:` lines to reflect new status. If section not found, append it.
   - Per D-06: Add/update `approval_status` in CHANGE-SPEC.md frontmatter. If no frontmatter exists, prepend one with `approval_status` field.
   - Return `{ ok: true, change_id, approval_status }` on success, `{ ok: false, error: { code, message } }` on failure
   - Use `resolveChangeWorkspace` from intake module to resolve paths

4. **hasCriticalUnresolved(seeds: DiscussionSeed): boolean**: Return true if `seeds.ambiguities` contains any item with `severity === 'critical'`. This is the gate check for DISC-05.
</action>

<acceptance_criteria>
- `writeResolvedSection` appends `## Resolved` section to CHANGE-SPEC.md without removing original `## Ambiguities`, `## Conflicts`, or `## Open Questions` sections
- `writeResolvedSection` appends `## Acceptance Criteria` and `## Scope` sections with `### In Scope` / `### Out of Scope` subsections
- Calling `writeResolvedSection` twice replaces the previous `## Resolved` section instead of duplicating it
- `updateApprovalStatus(projectRoot, changeId, 'approved')` writes `approval_status: approved` in CHANGE-SPEC.md frontmatter AND sets `status: 'approved'` in STATUS.json
- `updateApprovalStatus` returns `{ ok: false }` with error when workspace does not exist
- `hasCriticalUnresolved` returns `true` when any ambiguity has `severity === 'critical'`, `false` when none do
- Module compiles with `npx tsc --project tsconfig.build.json` without errors
</acceptance_criteria>

<read_first>
- src/ndd-command-router.cts (discuss branch added in 04-01)

- .planning/phases/04-discuss-and-approve-change-spec/04-CONTEXT.md (D-07 explicit user approval, D-08 dual-write, D-09 plan-phase gate)
</read_first>

<action>
1. **Router update** — In `src/ndd-command-router.cts`, extend the `discuss` branch to also support a sub-action for updating approval status. The router should handle:
   - `gsd-tools ndd discuss <change-id>` — returns discussion context (already done in 04-01)
   - `gsd-tools ndd discuss-update <change-id> <status>` — calls `discuss.updateApprovalStatus(cwd, changeId, status)` and outputs the result. Validate `status` is one of `draft`, `discussed`, `approved`. Add as a new top-level subcommand `discuss-update` in the router.

2. **Add approve gate to router** — Add `gsd-tools ndd discuss-check <change-id>` subcommand that:
   - Reads CHANGE-SPEC.md and calls `extractAmbiguities`
   - Calls `hasCriticalUnresolved` on the result
   - Returns JSON `{ change_id, approved: boolean, has_critical_unresolved: boolean, critical_count: number }`
   - This is what `ndd-plan-phase` (Phase 5) will call to enforce DISC-05

3. **Workflow update** — Update `commands/ndd/discuss-phase.md` `<process>` to include:
   - After resolving ambiguities, call `gsd-tools ndd discuss-update <change-id> discussed`
   - After user approves, call `gsd-tools ndd discuss-update <change-id> approved`
   - Include explicit step: "Ask the user: 'All critical ambiguities have been resolved. Do you approve this change spec for planning?' — do NOT auto-approve per D-07"
   - Reference `gsd-tools ndd discuss-check <change-id>` as the gate check
</action>

<acceptance_criteria>
- `gsd-tools ndd discuss-update <change-id> approved` updates both STATUS.json and CHANGE-SPEC.md
- `gsd-tools ndd discuss-update <change-id> invalid-status` returns an error
- `gsd-tools ndd discuss-check <change-id>` returns JSON with `approved`, `has_critical_unresolved`, and `critical_count` fields
- Router unknown subcommand error message includes `discuss-update` and `discuss-check` in the available list
- `commands/ndd/discuss-phase.md` contains the string `discuss-update` and `discuss-check`
- `commands/ndd/discuss-phase.md` contains text about explicit user approval (not auto-approve)
</acceptance_criteria>
