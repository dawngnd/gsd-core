### Task 2: Implement `runImpactDiscovery()` Orchestrator

<action>
Add an exported function `runImpactDiscovery(opts: { projectRoot: string, changeId: string }): ImpactDiscoveryResult` to `src/ndd-impact-discovery.cts`.

The function performs the deterministic preparation layer (no LLM reasoning):

1. **Validate change-id**: Call `intake.validateChangeId(opts.changeId)`. If invalid, return `{ ok: false, error: { code: 'invalid_change_id', message } }`.

2. **Resolve workspace**: Call `intake.resolveChangeWorkspace(opts.projectRoot, opts.changeId)`. If not ok, return `{ ok: false, error: { code: 'workspace_resolution_failed', message } }`.

3. **Check workspace exists**: Verify `workspace_dir` exists and contains `STATUS.json`. If not, return `{ ok: false, error: { code: 'workspace_not_found', message: 'Change workspace not found. Run ndd-change first.' } }`.

4. **Read STATUS.json**: `JSON.parse(fs.readFileSync(path.join(workspace_dir, 'STATUS.json'), 'utf-8'))`. Verify `phase` is `'intake'` or later (not empty). If STATUS.json is unparseable, return error with code `'invalid_status'`.

5. **Check codebase map**: Call `checkCodebaseMapAvailability(opts.projectRoot)`. Store result.

6. **Load capability config**: Call `loadCodebaseCapabilityConfig(opts.projectRoot)`. Store result.

7. **Read CHANGE-SPEC.md**: Read from workspace. Extract requirement sections with `extractRequirementSections()`.

8. **Build initial IMPACT.md scaffold**: Call `renderImpactMarkdown()` with empty groups (one per extracted requirement, each with empty entries array) and empty cross-cutting. This is the initial scaffold — the LLM workflow populates it with actual impact entries.

9. **Write IMPACT.md**: Use `platformWriteSync(path.join(workspace_dir, 'IMPACT.md'), renderedMarkdown)`.

10. **Update STATUS.json**: Read existing, set `phase: 'impact'`, add `artifacts.impact: 'IMPACT.md'`, refresh `updated_at` to `new Date().toISOString()`. Write back with `platformWriteSync`.

11. **Return success**: `{ ok: true, change_id, impact_path, relative_impact_path, codebase_map_available: mapResult.available, codebase_map_files: mapResult.files, capability_config: capConfig, summary: { confirmed: 0, likely: 0, unknown: 0 } }`
</action>

### Task 3: Replace `commands/ndd/impact.md` with Full Workflow Prompt

<action>
Replace the entire body of `commands/ndd/impact.md` (after the existing frontmatter lines 1–13 which stay unchanged) with the full impact discovery workflow prompt.

**Frontmatter** (keep existing lines 1–13 as-is, they already have correct `name: ndd:impact`, `argument-hint`, `effort`, `allowed-tools`).

**`<objective>`**: Discover likely affected code areas for an NDD change using codebase maps, capability-based tool selection, and LLM source inspection. Write a structured `IMPACT.md` grouped by CHANGE-SPEC requirements.

**`<execution_context>`**:
- `@.planning/PROJECT.md`
- `@.planning/codebase/ARCHITECTURE.md`
- `@.planning/codebase/STRUCTURE.md`

**`<process>`** (ordered steps):

Step 1 — Run deterministic helper:
```bash
node .agents/gsd-core/bin/gsd-tools.cjs ndd impact <change-id>
```
Fallback: `node gsd-core/bin/gsd-tools.cjs ndd impact <change-id>`

Parse the JSON result. If `ok: false`, report the error and stop.

Step 2 — Report tool availability to user:
- For each tool in `capability_config.tools`, if `available: true`: report `✓ <tool> available — using <capabilities>`
- If tool not available: report `⚠ <tool> not available — <fallback description>`

Step 3 — Handle missing codebase map:
- If `codebase_map_available: false`: warn user and present three choices:
  (1) Run `/gsd:map-codebase` first (recommended)
  (2) Continue with lightweight discovery (grep + LLM reasoning only)
  (3) Cancel
- If user chooses (1), stop and tell them to run map-codebase first
- If user chooses (3), stop
- If user chooses (2), proceed with available tools only

Step 4 — Read context:
- Read `.planning/codebase/*.md` files (from `codebase_map_files` in result)
- Read `CHANGE-SPEC.md` from the change workspace
- Read `SOURCE-MANIFEST.md` from the change workspace
- Read source documents under `sources/` in the change workspace

Step 5 — Wiki enrichment (if wiki tool available):
- Query wiki/knowledge base about change requirements for domain context
- Tag findings with `discovered_by: wiki.knowledge`

Step 6 — CodeGraph analysis (if codegraph tool available):
- For each requirement, query callers/callees/impact_analysis/symbol_lookup
- Tag findings with `discovered_by: codegraph.<capability>`

Step 7 — LLM source inspection:
- Based on codebase map context and CHANGE-SPEC requirements, identify relevant source files
- Use `grep_search` to find matching patterns in codebase
- Read and reason about identified source files
- Assign confidence: `confirmed` for direct code path matches, `likely` for same-module/shared-data relationships, `unknown` for possible but unproven
- Tag findings with `discovered_by: grep_search`, `codebase_map`, or `llm_reasoning`

Step 8 — Write final IMPACT.md:
- Read the scaffold IMPACT.md from step 1
- Replace scaffold with actual populated impact entries grouped by requirement
- Update summary table counts
- Update frontmatter `status` from `draft` to `complete`
- Write to `.planning/ndd/changes/<change-id>/IMPACT.md`

**`<success_criteria>`**:
- `IMPACT.md` exists at `.planning/ndd/changes/<change-id>/IMPACT.md`
- Every requirement from CHANGE-SPEC has an impact section (even if "None identified")
- Each impact entry has file path, evidence, source reference, and discovered_by attribution
- Tool availability was reported to the user before analysis
- Missing codebase map was handled with user choice (not silently skipped)
- STATUS.json phase is `impact` and `artifacts.impact` is `IMPACT.md`
