# Requirements: NDD Brownfield Change Workflow

**Defined:** 2026-07-07
**Core Value:** Turn messy project-specific change documents into an approved, impact-aware implementation scope that can safely reuse GSD's existing planning, subagent execution, verification, and shipping loop.

## v1 Requirements

### Namespace

- [x] **NDD-01**: User can invoke NDD workflow commands under the fixed `ndd` namespace without replacing existing `gsd` commands.
- [x] **NDD-02**: NDD commands install through the existing runtime artifact system for supported command/skill surfaces.
- [x] **NDD-03**: NDD artifacts are stored under `.planning/ndd/changes/<change-id>/`.

### Change Intake

- [x] **INTK-01**: User can start a change workflow by providing a folder of Markdown documents.
- [x] **INTK-02**: `ndd-change` creates a stable change id and initializes `.planning/ndd/changes/<change-id>/`.
- [x] **INTK-03**: `ndd-change` writes `SOURCE-MANIFEST.md` listing ingested source files and their roles when inferable.
- [x] **INTK-04**: `ndd-change` writes a draft `CHANGE-SPEC.md` summarizing goals, source-backed requirements, constraints, ambiguities, conflicts, and open questions.
- [x] **INTK-05**: Ingestion preserves source traceability for extracted business/API/proposal claims.

### Impact Discovery

- [x] **IMPT-01**: `ndd-impact` reads `.planning/codebase/*` as baseline codebase knowledge.
- [x] **IMPT-02**: `ndd-impact` inspects relevant source files based on the change start point and source documents.
- [x] **IMPT-03**: `ndd-impact` writes `IMPACT.md` with confirmed, likely, and unknown affected areas.
- [x] **IMPT-04**: `IMPACT.md` records evidence paths and confidence levels for each affected area.

### Discussion and Spec Approval

- [x] **DISC-01**: `ndd-discuss-phase` uses `CHANGE-SPEC.md`, `IMPACT.md`, source docs, and codebase map context to ask targeted clarification questions.
- [x] **DISC-02**: `ndd-discuss-phase` explicitly resolves ambiguous or conflicting business/API requirements before planning.
- [x] **DISC-03**: `ndd-discuss-phase` updates `CHANGE-SPEC.md` with in scope, out of scope, assumptions, acceptance criteria, and unresolved non-blocking notes.
- [x] **DISC-04**: User can approve `CHANGE-SPEC.md` before implementation planning begins.
- [x] **DISC-05**: Critical unresolved ambiguity prevents `ndd-plan-phase` from proceeding.

### GSD Bridge and Planning

- [x] **PLAN-01**: `ndd-plan-phase` validates that the target change has an approved `CHANGE-SPEC.md`.
- [x] **PLAN-02**: `ndd-plan-phase` creates or updates bridge context so GSD planning mechanics can consume the NDD change.
- [x] **PLAN-03**: `ndd-plan-phase` reuses GSD planning conventions, plan-check behavior, source grounding, and existing planner references where possible.
- [x] **PLAN-04**: NDD records the link between the change id and any GSD phase/plan artifacts in `phase-link.md` or equivalent metadata.

### Execution

- [x] **EXEC-01**: `ndd-execute-phase` reuses GSD execution mechanics and subagent coordination for an approved/planned NDD change.
- [x] **EXEC-02**: Execution summaries remain traceable to the originating NDD change id.
- [x] **EXEC-03**: NDD does not fork or duplicate GSD executor core behavior.

### Verification and Ship

- [x] **VERF-01**: `ndd-verify-work` verifies completed work against `CHANGE-SPEC.md` acceptance criteria.
- [x] **VERF-02**: `ndd-verify-work` writes verification output under the NDD change folder or links to GSD verification artifacts.
- [x] **SHIP-01**: `ndd-ship` reuses GSD ship behavior where possible.
- [x] **SHIP-02**: `ndd-ship` enriches PR/review context with `CHANGE-SPEC.md`, `IMPACT.md`, and verification evidence.

### Maintainability

- [x] **MNT-01**: NDD workflows reuse GSD core helpers instead of reimplementing state, git, phase, roadmap, drift guard, executor, verifier, or ship logic.
- [x] **MNT-02**: NDD-specific behavior is implemented at workflow, agent, prompt, template, and adapter layers.
- [x] **MNT-03**: Tests cover NDD command routing/install surface and core artifact generation paths.

## v2 Requirements

### Change Management

- **CHG-01**: User can list, resume, cancel, or archive NDD changes.
- **CHG-02**: User can refresh impact discovery after source files change.
- **CHG-03**: User can run a single command that chains intake, impact, discussion, planning, execution, verification, and ship with configured gates.

### Integrations

- **INTG-01**: NDD can ingest issue tracker exports or URLs in addition to local Markdown folders.
- **INTG-02**: NDD can generate a reusable project-specific business glossary from repeated source documents.

### Reporting

- **RPT-01**: NDD can produce a change history dashboard or index across `.planning/ndd/changes/`.
- **RPT-02**: NDD can summarize recurring ambiguity/conflict patterns across business documents.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Full independent NDD planner/executor/verifier core | Reuse GSD core mechanics to avoid drift and duplicate maintenance |
| Greenfield product ideation flow | Existing `gsd-new-project` already owns this use case |
| Requiring clean source documents | NDD exists specifically because project documents can be unclear or conflicting |
| Directly storing every draft change in `ROADMAP.md` | NDD discovery lifecycle should remain separate until implementation is approved |
| Runtime support for unsupported non-GSD namespaces without installer changes | Namespace installation must be integrated deliberately with runtime artifact logic |
